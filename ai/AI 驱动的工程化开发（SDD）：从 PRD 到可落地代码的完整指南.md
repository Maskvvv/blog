### AI 驱动的工程化开发：从 PRD 到可落地代码的完整指南

> 在 AI 编程时代，如何将模糊的需求转化为可控、可审计的高质量代码？本文整理了一套融合 OpenSpec 与深度拷问（grill）的工程化工作流，特别适合 Java 后端开发者在企业级项目中落地 AI 辅助开发。

------

### 一、引言：AI 编程的痛点与破局

当前，使用 AI 辅助编程（如 Cursor、Claude Code）已渐成常态，但开发者常面临三大困境：

- **需求漂移**：AI 在对话中容易偏离初始需求
- **幻觉与不一致**：AI 可能生成不存在的接口或重复的代码
- **文档缺失**：代码完成后缺少设计文档，成为“黑盒”

这些问题在团队协作和企业级项目中尤为致命。OpenSpec 正是为解决这些问题而生的一套**规范驱动开发（Spec-Driven Development, SDD）** 框架。

------

### 二、OpenSpec：规范驱动的 AI 开发框架

#### 2.1 核心理念

OpenSpec 倡导“**棕地优先（Brownfield-first）**”原则——它不仅适用于新项目，也能通过“增量（Delta）机制”平滑地接入并管理现有代码库的演进。

其核心思想是：**在编写代码前，强制开发者和 AI 就“要构建什么”达成清晰、可验证的共识，并将其记录为“活的规范”**。

#### 2.2 核心架构：目录结构与“单一事实来源”

OpenSpec 将项目状态清晰地分为两个核心区域：

text

```
openspec/
├── specs/          # 单一事实来源：存放当前已实现功能的最终规范
└── changes/        # 变更提案：存放所有进行中的变更
    └── add-order-query/
        ├── proposal.md    # 为什么做（Why）和做什么（What）
        ├── design.md      # 技术方案（How）
        ├── specs/         # 规格增量（Deltas）
        └── tasks.md       # 实施清单
```



#### 2.3 核心工作流（斜杠命令）

OpenSpec 的工作流是一个 **“提案 → 实施 → 归档”** 的闭环：

| 命令            | 作用                               |
| :-------------- | :--------------------------------- |
| `/opsx:propose` | 根据需求创建结构化的变更提案       |
| `/opsx:apply`   | 严格按照提案中的任务清单编写代码   |
| `/opsx:archive` | 功能完成后，将增量规范合并到主规范 |
| `/opsx:explore` | 在想法模糊时进行探索性讨论         |
| `/opsx:verify`  | 验证代码是否与规范一致             |

### 三、从 PRD 到代码：Java 后端的五步落地法

#### 3.1 前期准备：建立项目“宪法”与知识库

在启动任何 AI 编码前，建议先建立以下基础：

| 文件                                          | 作用                                                         |
| :-------------------------------------------- | :----------------------------------------------------------- |
| **`AGENTS.md`**                               | AI 的入口文件，包含工作流程、必读文档位置和保护目录          |
| **`docs/architecture/implicit-contracts.md`** | **核心中的核心**。记录团队口头约定、历史“坑点”和特殊业务规则 |
| **`docs/standards/testing.md`**               | 测试规范                                                     |
| **`docs/standards/database.md`**              | 数据库与 SQL 规范                                            |

------

#### 3.2 核心流程：五步法详解

##### 第一步：需求理解与 PRD 精读

将模糊的业务需求转化为清晰、可量化、无歧义的技术语言：

| ❌ 模糊需求     | ✅ 清晰技术语言                            |
| :------------- | :---------------------------------------- |
| “提升系统性能” | “订单查询接口的 P95 响应时间需低于 200ms” |

**建议**：同时明确列出本次“不做什么”，划定 AI 的“红线”。

##### 第二步：创建变更提案（`/opsx:propose`）

在 AI 工具中输入命令：

bash

```
/opsx:propose add-order-query
```



用结构化的提示词描述需求：

> **背景与目标**: [简述业务背景和要解决的问题]
> **核心功能**:
>
> 1. 支持按 `orderId`、`userId`、`startTime`、`endTime` 查询
> 2. 支持分页，每页默认 20 条
> 3. 返回结果包含订单基本信息和商品明细
>    **非功能性需求**: 接口响应时间 P95 < 200ms
>    **边界与约束**: 本次不涉及订单状态修改，查询时间范围默认最近 3 个月

AI 会生成 `proposal.md`、`design.md`、`specs/`（增量规范）和 `tasks.md`。

##### 第三步：人工审查与规范精修

**这是最关键的一步，人是决策者**。仔细审查 AI 生成的四个文件，确保规范准确无误。如有偏差，直接修改文档或废弃重开。

##### 第四步：AI 执行实现（`/opsx:apply`）

执行命令：

bash

```
/opsx:apply
```



AI 严格按照 `tasks.md` 的顺序逐项完成任务，并在完成后标记为 `✓`。

##### 第五步：验证与归档（`/opsx:verify` & `/opsx:archive`）

bash

```
/opsx:verify   # 自动检查代码是否与规范一致
/opsx:archive  # 将增量规范合并到主规范，完成闭环
```

### 四、提效工具与深度拷问（Grill）

#### 4.1 需求转化提效工具

| 工具                              | 核心能力                                                     |
| :-------------------------------- | :----------------------------------------------------------- |
| **`/opsx:propose`**               | 与 OpenSpec 流程无缝集成，自动生成结构化提案                 |
| **PRD Task Decomposition System** | 自动将 PRD 拆分为前后端开发任务                              |
| **specx**                         | 企业级研发流程 skill 集，提供需求拆解、澄清、设计等原子化步骤 |
| **MetaGPT**                       | 多智能体协作框架，模拟产品经理、架构师、开发工程师分工       |

#### 4.2 `grill-me`：深度拷问你的需求

`grill-me` 是一个 AI 编程助手技能，核心理念是**在写代码前，让 AI 通过结构化提问帮你把需求彻底想清楚**。

- **一次只问一个问题**，每个问题都自带“参考答案”
- **能自己查的绝不问你**：主动查阅代码库寻找答案
- **适合场景**：大型项目启动、复杂功能设计、技术方案评审

##### 安装与使用

bash

```
npx skills add https://github.com/mattpocock/skills --skill grill-me
```



在 AI 助手（如 Cursor）中输入 `/grill-me` 后跟你的初步想法即可。

> **工作流建议**：先用 `/grill-me` 拷问需求，然后让它帮你整理成 `PLAN.md`，再让 AI 依据这份清晰的计划去执行代码。

#### 4.3 `grill-with-docs`：带知识沉淀的拷问

这是 `grill-me` 的**工程化升级版**，除了拷问，还会自动维护两份核心文档：

- **`CONTEXT.md`**（项目术语表）：统一记录核心术语的精确含义
- **ADR（架构决策记录）**：记录重要的技术决策及其原因

##### 安装与使用

bash

```
npx skills add https://github.com/mattpocock/skills/tree/main/skills/engineering/grill-with-docs
```



触发方式：

- 斜杠命令：`/grill-with-docs`
- 触发短语：“grill me with docs”、“grill on the design”等

### 五、企业级工程化落地全景图

#### 5.1 推荐工作流（完整版）

text

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  1. PRD精读  │───▶│ 2. 需求拷问  │───▶│ 3. 创建提案  │───▶│ 4. 规范审查  │───▶│ 5. AI实施   │
│             │    │ (grill-*)   │    │ (/propose)  │    │   (人)      │    │ (/apply)   │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
                                                                                          │
                                                                                          ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  9. 持续优化 │◀───│  8. 归档    │◀───│  7. 验证    │◀───│  6. 代码审查 │◀───│             │
│             │    │ (/archive)  │    │ (/verify)   │    │   (人)      │    │             │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```



#### 5.2 企业级“硬护栏”

| 措施                     | 说明                                                         |
| :----------------------- | :----------------------------------------------------------- |
| **权限配置**             | 在 `settings.local.json` 中禁止 AI 执行 `git push`、`kubectl` 等危险命令 |
| **自动化检查**           | CI 流水线中集成 `openspec validate`，自动检查变更提案格式    |
| **封装团队能力**         | 将代码评审、架构审查、SQL 风险检查封装为可复用的技能         |
| **实现、评审、验证分离** | AI 负责实现（`/apply`），人负责审查，独立命令负责自动验证    |

#### 5.3 关于 Harness

在技术讨论中，“Harness”可能指：

- **AI 领域的 Harness Engineering**：为 AI 智能体构建运行环境、约束规则和反馈闭环的工程范式
- **DevOps 领域的 Harness 平台**：一个 AI 驱动的智能 DevOps 平台，提供 CI/CD、测试自动化等一站式服务

### 六、总结与实践建议

| 核心理念     | 说明                                               |
| :----------- | :------------------------------------------------- |
| **慢即是快** | 在编码前花时间把需求想清楚，是效率最高的做法       |
| **规范先行** | 将“需求”从想法转化为结构化的、人机可读的“技术契约” |
| **人机协作** | AI 负责执行，人负责决策和审查                      |
| **知识沉淀** | 让每次开发都留下可追溯的文档和架构决策记录         |

**建议的起步路径**：

1. 先在一个**中等复杂度**的需求上试用 `/opsx:propose` 和 `/grill-me`
2. 跑通“提案 → 实施 → 归档”的完整闭环
3. 逐步引入 `grill-with-docs` 进行知识沉淀
4. 当流程成熟后，推广到核心业务模块
